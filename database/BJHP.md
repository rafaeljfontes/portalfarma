# Instalação do módulo BJHP

HTTPS: o cliente usa `application/certificates/cacert.pem` para validar o certificado da OJS. Pode ser substituído pelo caminho absoluto em `BJHP_OJS_CA_BUNDLE`. Mantenha esse pacote de autoridades certificadoras atualizado. Falhas de transporte apresentam o código cURL sem expor a URL autenticada ou o token.

1. Configure no ambiente do PHP/Apache: `BJHP_OJS_URL`, `BJHP_OJS_TOKEN`. O módulo reutiliza a conexão `default` de `application/config/database.php`, no banco `web_site`. Não são necessárias credenciais BJHP_DB separadas. A URL deve ser HTTPS e terminar em `/api/v1`, incluindo o caminho da revista e `index.php` quando necessário. Não inclua token na URL configurada nem no repositório.
2. Compare o esquema existente de `bjhp_artigos` e `bjhp_edicoes` com `database/bjhp.sql` antes de executar o SQL no banco `web_site`. O histórico e os membros do corpo editorial usam respectivamente `importacoes` e `bjhp_corpo-editorial`, também em `web_site`. O arquivo cria tabelas novas, mas não migra tabelas preexistentes. As quatro tabelas precisam de InnoDB para rollback. Nenhum SQL é executado automaticamente pela aplicação.
3. Configure uma conta OJS com acesso de leitura a todas as submissões publicadas da revista. O adaptador foi preparado para a API OJS 3.3 (`issues`, `submissions`, detalhes de `publications`, paginação `items/itemsMax`, autenticação `apiToken`). Confirme a versão instalada antes da ativação. Referência: https://docs.pkp.sfu.ca/dev/api/ojs/3.3
4. Em Gerenciar usuários, atribua explicitamente `BJHP`. A permissão `admin` isolada não libera o módulo. Entre novamente para atualizar o menu de uma sessão antiga. As rotas verificam a permissão e o status atuais no banco em cada acesso.
5. Acesse `restrito/bjhp/importar` e execute uma importação de homologação. Confira totais, edição dos artigos e o registro do usuário. Teste também acesso sem permissão, sessão expirada e falha da API.

O fluxo importa somente edições e artigos publicados. Identifica registros por `ojs_issue_id` e `ojs_article_id`, preservando os IDs locais e associando `bjhp_artigos.edicao_id` a `bjhp_edicoes.id`. O mapeamento usa as colunas existentes (identificação, título, datas, autores, DOI, páginas e URLs). Edições, artigos e histórico são gravados na mesma transação. O histórico registra apenas importações concluídas; falhas mantêm o histórico anterior. Um lock MySQL impede importações simultâneas. Como as tabelas existentes não têm índices únicos nem AUTO_INCREMENT, o módulo consulta o ID OJS antes de inserir/atualizar e aloca novos IDs sob esse lock. Outros processos que escrevam nessas tabelas devem respeitar o mesmo lock. IDs OJS duplicados interrompem a importação. O SQL para instalações novas inclui PRIMARY KEY e UNIQUE; não altera índices das tabelas existentes. Configure PHP e MySQL com o mesmo fuso horário.

O cadastro de membros do corpo editorial grava em `web_site.bjhp_corpo-editorial`: categoria, nome, titulação, instituição, cidade, estado, país, ORCID, URL do ORCID, foto (upload PNG/JPG de até 2 MB, com caminho gerado pelo servidor), minicurrículo, e-mail, ordem de exibição e status. Nome, categoria, ordem e status são obrigatórios no formulário. ID e datas são preenchidos automaticamente. Não depende de edições importadas. O lock `bjhp_corpo_editorial_cadastro` serializa a geração do ID, pois a tabela não possui AUTO_INCREMENT; outros processos de cadastro devem respeitar esse lock. A tabela antiga `editoriais` não é mais utilizada pelo módulo e seus dados não são excluídos.

Cada chamada externa tem timeout de 45 segundos. Para acervos grandes, ajuste os limites do PHP/Apache/proxy para a duração total da importação. Uma interrupção HTTP exige conferir o histórico antes de repetir. O token é enviado apenas do backend à OJS; configure o servidor OJS para não registrar o parâmetro `apiToken` nos logs de acesso.

Validação automatizada sem rede ou banco: `php tests/bjhp_ojs_test.php`. A homologação real exige as configurações e o esquema acima.
